# Field report — first live engagement

**Date:** 2026-08-20
**Against:** a real Jira and Confluence site (`greenfield-dev.atlassian.net`)
**Engagement:** Harbour Freight Co, a fictional freight dispatch MVP, run
end to end from `/new-engagement` to handoff.

Everything below was done by following each command's markdown literally,
against live infrastructure. It is the first time this plugin has touched a
tracker.

## What was exercised

| | |
|---|---|
| OAuth to the Atlassian MCP server | authorised, then **re-**authorised |
| Epic, stories, sub-tasks | 16 issues created: `KAN-1` → 7 stories → 8 sub-tasks |
| Acceptance criteria | copied verbatim from the signed baseline into each story |
| Write-back | 8 real issue keys into `tasks.md`, header preserved |
| Status pull | issues transitioned in Jira, status read back |
| Confluence | a client-facing status page published to space `SD` |
| All five gates | artifacts produced, two sign-offs recorded against real SHAs |
| `/conform` | run at every stage; ended 13 passed, 0 failed, 0 not checked |

## Four defects, all now fixed

### 1. The consent screen can refuse before authorisation begins

Atlassian's consent screen showed **"Supported sites required — your account
isn't currently associated with a supported site"**, with *0 of 0 permissions*
and Accept greyed out. The account had no Jira site attached, so there was
nothing to grant.

`tracker-jira` documented three failure modes and **every one assumed
authorisation had completed** — wrong account, not in the project, not a member
of the site. Someone hitting this would have read a troubleshooting table
describing symptoms they could not reach.

### 2. Status mapping by name does not survive a real Jira

Jira's **default** software workflow includes **In Review**, which is none of
the five values `tasks.md` allows. The existing rule — *a tracker state that
does not map cleanly is a mapping decision, stop and ask* — held correctly and
refused to guess. That is the right instinct, but it means `/sync-tracker`
stops and asks on the most common workflow in existence, every time.

The live response showed the better abstraction: "In Review" carries
`statusCategory: indeterminate`. Every Jira status, however customised, belongs
to exactly one of three categories. Matching on the **category** works on any
workflow; matching on the **name** survives only the project it was written for.

### 3. A status pull would have erased `blocked` and `dropped`

This is the one no amount of desk-checking would have found, and it is a
data-loss bug.

`blocked` and `dropped` have no tracker equivalent. A blocked task usually sits
in an ordinary in-flight status; a dropped one is often still open. So a
category-based pull would write `in-progress` over both and **silently erase
the two states most worth reporting** — that work is stuck, or that scope was
cut. A pull now touches only `todo`, `in-progress` and `done` rows, and reports
the rest rather than absorbing them.

### 4. The unattended tier assumes an app nobody was told to install

The methodology's Atlassian advantage is the unattended tier: assign a Jira
item to Claude, it works in a sandbox and opens a draft pull request. That is
the reason `CLAUDE.md` is called technically load-bearing.

Searching the live site's assignable users for `Claude` returned **0 matches**.
The app is not installed, and `tracker-jira` said "select **Claude** in the
assignee dropdown" without a word about installing it or any way to check. On a
client-owned site that is a client decision and can take weeks.

Worse, the failure is silent: an item assigned to nobody looks exactly like an
item waiting on an agent, so the work simply does not happen and nothing says
so.

## What held up

Worth recording, because these are the claims the methodology makes:

- **`(pending)` discipline.** Nothing invented an identifier at any point. The
  epic field stayed `(pending)` until Jira returned `KAN-1`; every `Item` cell
  stayed `(pending)` until a real key existed. Eight keys were written, and all
  eight came from an API response.
- **Verbatim acceptance criteria.** Each story carries its requirement's
  criterion word for word, so the tracker and the signed baseline agree.
- **Sign-off against a SHA.** Both gates recorded the commit of the approved
  artifact; `/conform` re-checks each and reports drift rather than trusting.
- **No internal shorthand on the client page.** The published Confluence page
  contains no requirement number, task ID or issue key — the rule survived a
  real report, which is where it is tempting to break.
- **Honest coverage at handoff.** Two of seven requirements were not met and
  neither was rounded up: N1 is recorded **unverified** (no load environment
  was available) rather than met, and N2 **outstanding** — six-year retention
  cannot be demonstrated inside six weeks. The second was raised in the status
  report *before* acceptance rather than discovered at it.

## Limits of this run

- One person following the commands, not a model executing them unattended.
- Jira and Confluence only. **Azure DevOps has never been run at all.**
- **No software was actually built, and nothing was executed by an agent.** The
  build phase moved task states in a markdown file. The eight Jira sub-tasks
  are unassigned and untouched. This run exercised the record-keeping half of
  the methodology — gates, sign-offs, tracker sync, reporting — and none of the
  execution half. The unattended tier remains entirely unproven, and cannot be
  proven on a site without the Claude app installed.
- One engagement on a fresh site. Nothing here says how this behaves on a Jira
  with years of customisation behind it.
